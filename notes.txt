TOOLS & ENVIRONMENT
================================================================================

CMAKE:
- CMake is a build system GENERATOR — it does NOT compile code
- Reads CMakeLists.txt and generates instructions (Makefiles) for Make to follow
- Analogy: CMake is the ARCHITECT, Make is the CARPENTER

CMAKE WORKFLOW:
  mkdir build
  cd build
  cmake ..    <- points CMake at parent directory where CMakeLists.txt lives
  make        <- actually compiles and links

WHEN TO RUN cmake .. vs make:
- cmake ..: only when project STRUCTURE changes (new files, new dirs, CMakeLists.txt)
- make: anytime you change code inside existing files
- INCREMENTAL BUILDS: Make only recompiles files that changed

CMakeLists.txt STRUCTURE:
  cmake_minimum_required(VERSION 3.10)
  project(projectName)
  add_executable(targetName source.cpp)
  target_include_directories(targetName PRIVATE folderName)

  - add_executable MUST come before target_include_directories
  - ACCESS LEVELS: PRIVATE (this target only), PUBLIC (this + dependents), INTERFACE (dependents only)

HOW #include WORKS:
- #include = copy-pasting the header into the file that includes it
- Compiler ONLY sees files pulled in via #include or add_executable
- Header sitting on disk is invisible to compiler until included
- Syntax error in header won't show until something includes it

COMPILER vs IDE — HOW THEY FIND HEADERS:
- Two separate systems — compiler uses CMakeLists.txt, IDE has its own system
- IDE include error does NOT mean code won't compile — always check make first
- Fix: CMake Tools extension in VS Code + run CMake: Configure

INTELLISENSE (VS Code):
- Powers autocomplete, parameter hints, error highlighting, go-to-definition
- Needs to be synced with CMake — run CMake: Configure or reset IntelliSense database
- Can disable inline suggestions while learning (good for building recall)

================================================================================
MEMORY MANAGEMENT
================================================================================

STACK vs HEAP:
- Stack: automatic, local variables and function calls, fixed size, freed on scope exit
  In embedded: blowing the stack (deep recursion, large locals) = crash, no OS to save you
- Heap: intentional, requested with new, YOU must free with delete
  Unpredictable timing — bad for real-time systems

ALLOCATING & FREEING:
  new T[n]    <- allocate array on heap, returns address of first element
  delete[] p  <- free array heap memory (runs destructor on each element)
  delete p    <- free single object heap memory
  ALWAYS match: new[] with delete[], new with delete — compiler won't catch mismatches

WHAT delete[] ACTUALLY DOES:
- Runs destructor on each element (if T has one)
- Returns memory to heap — marks it available again
- Does NOT touch the pointer — pointer still holds old address (dangling pointer risk)

DELETE ORDER MATTERS:
  Wrong: m_data = newData;  then  delete[] newData;  <- deletes what you just assigned!
  Right: delete[] m_data;   then  m_data = newData;  <- free old first, then reassign

WHAT A POINTER ACTUALLY IS:
- Just a number — a memory address in hexadecimal (e.g. 0x7f8b4c002a00)
- m_size = 4 (the number IS the value), m_data = 0xAAA (the number is a LOCATION)
- "The map, not the territory"
- On 64 bit system: pointer is 8 bytes regardless of what it points to

WHY POINTERS ARE FAST:
- Passing large object by value = copying every byte
- Passing by pointer/reference = copying one 8-byte address
- Always pass large objects by const reference: const T& not T

POINTER ARITHMETIC:
  array[i]  ==  *(array + i)  — identical, compiler does: base + (i * sizeof(T))
  Arrays must be contiguous — the math only works if elements are adjacent

LOCAL POINTER VARIABLES — no cleanup needed:
- Local variables live on the stack, destroyed automatically when scope ends
- Only delete heap memory (new), only nullptr member variables accessed after deletion
- Rule: stack takes care of itself, heap is YOUR responsibility

HOTEL ANALOGY:
- new = checking in, heap gives you a room number
- delete = checking out, room available again but number still exists in your hand
- Dangling pointer = holding a room number to a room that's been given to someone else

HEAP FRAGMENTATION:
- Long-running systems fragment heap: [used][free][used][free]
- Dynamic array CANNOT use fragmented memory — needs contiguous block
- Linked list CAN — each small node fits anywhere
- Embedded solution: static allocation (fixed buffers at compile time)

================================================================================
MEMORY MANAGEMENT ERRORS
================================================================================

MEMORY LEAK:
- Heap memory allocated but never freed
- Desktop: OS reclaims on exit. Bare metal embedded: gone until power cycle
- On a missile running 24/7: mission critical — a leak = eventual system failure
- Every new MUST have a matching delete

DANGLING POINTER:
- Pointer holding address to memory you no longer own (freed)
- Causes: deleting without nulling pointer, shallow copy + destructor
- Reading/writing through it = undefined behavior
- Fix: set to nullptr after deleting (if not immediately reassigning)

DOUBLE FREE:
- Calling delete on same memory block twice
- Caused by shallow copy — two objects pointing at same heap memory, both destructors run
- Result: undefined behavior, crash, silent corruption

SHALLOW COPY (leads to dangling pointer + double free):
- Default compiler copy copies pointer ADDRESS not heap DATA
- Two objects point at same block
- Destructor of one: other gets dangling pointer
- Destructor of both: double free

UNDEFINED BEHAVIOR:
- C++ standard doesn't define what happens — anything can occur
- Common causes: dangling pointer, double free, out of bounds, uninitialized vars
- Compiler will NOT always catch it
- In embedded: can corrupt other subsystem data, cause silent wrong behavior

OFF BY ONE:
- m_size = 3: valid indexes 0, 1, 2
- i < m_size  ✓    i <= m_size  ✗ (reads memory you don't own)

================================================================================
C++ CONCEPTS
================================================================================

RAII (Resource Acquisition Is Initialization):
- Tie resource lifetime to object lifetime
- Destructor cleans up automatically when object goes out of scope
- Prevents memory leaks

NULLPTR:
- Explicit "this pointer points at nothing" — always use instead of leaving uninitialized

SIZE_T:
- Unsigned integer for sizes and counts — can't be negative
- Matches platform size automatically (32 bit = 32 bit size_t)
- Lives in <cstddef>. Use for: size, capacity, indices, loop counters

FIXED WIDTH TYPES (<cstdint>):
- uint32_t, uint16_t, int8_t — guaranteed size regardless of platform
- Critical in embedded where hardware varies and resources are scarce

DECLARATION vs DEFINITION:
- Declaration: "this thing exists, here's its name and shape"
- Definition: the actual implementation, the body

TEMPLATES:
- Allow class/function to work with any type: template<typename T>
- typename and class are interchangeable (typename is more modern)
- DynamicArray<T> alone is invalid — T unknown, can't compile
- DynamicArray<int> triggers compiler to generate a concrete class for int
- Both declaration AND definition go in header — compiler needs full definition visible
- Regular classes can split .hpp/.cpp — templates cannot

CONCRETE vs ABSTRACT CLASS:
- Abstract: has pure virtual function, cannot be instantiated, defines interface
- Concrete: fully implemented, can be instantiated

IN-CLASS MEMBER INITIALIZATION (C++11):
  Node<T>* next = nullptr;  <- set at declaration
- Initializer list takes precedence if both present
- Good for simple defaults

DOT vs ARROW OPERATOR:
- . (dot): access member through object
- -> (arrow): access member through pointer — shorthand for (*ptr).member
- Linked lists use -> everywhere — nodes are always pointers

OPERATOR OVERLOADING:
- Redefine what operators do for custom types
- operator=  (copy assignment), operator[]  (subscript), operator+  (addition)

'this' POINTER:
- Pointer to the object the method was called on
- *this = the object itself
- Used in copy assignment: return *this

LAZY vs EAGER INITIALIZATION:
- Lazy: don't allocate until needed (right for embedded — scarce resources)
- Eager: allocate upfront (convenient but wasteful)

ASSERT:
  #include <cassert>
  assert(condition);  <- halts program if false, reports location
- Debug builds: active. Release builds (NDEBUG defined): compiles to nothing
- Use for: programmer errors, states that should never happen
- Embedded: use assert in debug, error codes in production, never exceptions

EXCEPTIONS IN EMBEDDED:
- Stack unwinding = unpredictable timing = breaks determinism
- Many embedded compilers disable exceptions entirely
- Rule: exceptions are off the table in embedded

TERNARY OPERATOR:
  condition ? value_if_true : value_if_false
  m_capacity = (m_capacity == 0) ? 1 : m_capacity * 2;

================================================================================
OOP & CLASS DESIGN
================================================================================

RULE OF THREE (C++03):
If you manage raw memory and define ANY of these, define ALL THREE:
1. Destructor          — free heap memory when object goes out of scope (~ClassName)
2. Copy constructor    — deep copy when creating new object from existing
3. Copy assignment     — deep copy when overwriting existing object (operator=)
WHY: compiler-generated versions do shallow copy = dangling pointer + double free

RULE OF FIVE (C++11+):
Adds to Rule of Three:
4. Move constructor   — transfer ownership (DynamicArray<T>&& other)
5. Move assignment    — transfer ownership on assignment
Move = hand over the pointer, don't copy. Much more efficient.
We write embedded-style C++ — Rule of Three first, move semantics later.

DESTRUCTOR:
- Runs automatically when object goes out of scope
- Syntax: ~ClassName() { }
- Linked list destructor must traverse and delete each node individually
  (each node is a separate heap allocation)
  Pattern: save next, delete current, advance
    while(m_head != nullptr) {
        Node<T>* next = m_head->next;
        delete m_head;
        m_head = next;
    }

COPY CONSTRUCTOR:
- Triggered when: DynamicArray<int> array2 = array1; (array2 is new)
- Signature: DynamicArray(const DynamicArray<T>& other)
- Must do deep copy — allocate new memory, copy data

COPY ASSIGNMENT OPERATOR:
- Triggered when: array2 = array1; (array2 already exists)
- Signature: DynamicArray<T>& operator=(const DynamicArray<T>& other)
- Returns *this to allow chaining (a = b = c)
- Extra steps: self-assignment guard + free existing memory first
  Steps: guard -> delete existing -> copy size/capacity -> allocate -> copy data -> return *this
- Self-assignment guard: if(this == &other) return *this;

ENCAPSULATION:
- Keep member variables private
- Expose behavior through public methods, not raw internals
- Getters for read access (size()), no direct pointer exposure

================================================================================
DATA STRUCTURES
================================================================================

DYNAMIC ARRAY:
Member variables: T* m_data, size_t m_size, size_t m_capacity
Growth strategy (doubling):
  1. Check if size == capacity
  2. New capacity = (capacity == 0) ? 1 : capacity * 2
  3. Allocate new heap block
  4. Copy old data
  5. Delete old block
  6. Point m_data at new block
  7. Add element, increment size
Big O: lookup O(1), append amortized O(1), insert middle O(n), growth O(n)

LINKED LIST:
Node struct: T value, Node<T>* next = nullptr
Member variables: Node<T>* m_head, Node<T>* m_tail, size_t m_size
- m_tail: O(1) append (without it: O(n) to find end)
- Use -> to access node members (nodes are always pointers)

Dynamic Array vs Linked List:
  Dynamic Array: O(1) lookup, O(n) insert/delete middle, needs contiguous memory
  Linked List:   O(n) lookup, O(1) insert/delete (with pointer), scattered memory OK
  Linked list advantage in embedded: works with fragmented heap

================================================================================
REAL TIME EMBEDDED SYSTEMS
================================================================================

EMBEDDED:
- Software on dedicated hardware with specific purpose
- Often: limited RAM, no hard drive, sometimes no OS (bare metal)
- Examples: microcontrollers, FPGAs, guidance systems

REAL TIME:
- Timing guarantees — operations MUST complete within X microseconds, every time
- Missing a deadline = correctness failure, not just performance problem
- KEY TERM: DETERMINISM — not just fast, predictably fast

FIRMWARE:
- Real software burned onto hardware, runs without OS
- "Burned" from old ROM chip days — now uses flash memory (erasable)
- Firmware engineers write C and C++ — real code, real bugs

WHY STL IS AVOIDED IN EMBEDDED:
- Dynamic allocation has unpredictable timing — breaks determinism
- STL overhead too large for resource constrained hardware
- Solution: roll your own — know exactly what code does and how long it takes

MEMORY vs RAM:
- RAM: physical hardware, stores data while running (where stack and heap live)
- Memory: broader — RAM, flash, ROM, cache, registers
- "Scarce resources" in embedded usually means RAM

STATIC ALLOCATION (to learn later):
- Fixed size buffers at compile time, no dynamic allocation
- Avoids fragmentation entirely — common in hard real-time systems

================================================================================
REAL-TIME SCHEDULING & CONCURRENCY
================================================================================

RTOS (Real-Time Operating System):
- Schedules tasks with timing guarantees
- Every task has a PRIORITY — scheduler runs highest priority READY task
- Task states: running, ready, blocked, sleeping

TASK PRIORITIES (missile system example):
- High:   Guidance — must run every few ms, life or death
- Medium: Telemetry — sending data to operators
- Low:    Logging — recording events

MUTEX (Mutual Exclusion):
- Locks shared resource so only one task accesses it at a time
- Prevents RACE CONDITIONS — two tasks reading/writing same data simultaneously
- Task locks -> does work -> unlocks. Other tasks block until unlocked.

RACE CONDITION:
- Two tasks access shared data simultaneously, result depends on timing
- Example: guidance reads sensor value while navigation writes new value mid-read
- Fix: mutex around shared resource

PRIORITY INVERSION:
- High priority task indirectly blocked by low priority task
- Scenario:
    1. Low priority locks mutex on shared sensor data
    2. High priority wakes up, needs mutex — BLOCKED
    3. Medium priority wakes up, doesn't need mutex — runs freely
    4. Medium runs while high waits on low = high effectively runs at low priority
- On a missile: guidance misses deadline = wrong course correction = mission failure

SOLUTIONS:
  Priority Inheritance (reactive):
  - Low priority task inherits high priority temporarily while holding mutex
  - Finishes fast, releases mutex, drops back to normal priority

  Priority Ceiling (proactive):
  - Mutex assigned ceiling = highest priority task that will ever use it
  - Any task locking mutex immediately runs at ceiling
  - Prevents inversion before it starts

MISSILE SOFTWARE ARCHITECTURE:
Each subsystem = its own RTOS task with priority
Communication: shared memory, message queues, publish-subscribe

- Guidance      — where am I, where going, what's my target

================================================================================
BIG O NOTATION
================================================================================
- How an algorithm SCALES as input grows — time and space complexity

O(1)     — constant, doesn't scale with input (array index lookup, hash map get)
O(n)     — linear, scales with input (copying all elements, linked list search)
O(n²)   — quadratic, nested loops (bubble sort)
O(log n) — logarithmic, binary search, very efficient
Amortized O(1) — occasional expensive operation averaged over many cheap ones
                 (dynamic array growth — rare O(n) copies, mostly O(1) appends)
